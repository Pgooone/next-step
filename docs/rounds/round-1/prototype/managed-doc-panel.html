Next-Step v2.0 · 设计文档

归属：设计阶段 · agent: designer · 提案时间 10 分钟前

§1 概述

Next-Step v2.0 是一条本地多 Agent 产线：把「一句想法」变成「可动工的设计包 + 可评审的原型」。产线每一步的产物都受管、可逐块签字、可追溯到上游；成品出缺陷时能沿追溯链归因到具体阶段，改完只重跑下游。

使命：让一个人用一队 AI，稳定产出别人敢接手动工的设计包与原型——过程全程可见、每步可签字、出错可归因、经验可复用。

任何新功能必须写明落在哪根柱子上：产能 / 可控 / 可追溯返工；写不出，不做。本次重构要解的三条病根：P1 没有主干判据、P2 概念膨胀（六并二）、P3 没有追溯链（块级 sourceRef 补地基）。

§2 技术选型

上游内核沿用 @earendil-works/pi-coding-agent monorepo。领域逻辑全部住在不认识 UI、也不认识 pi 的纯 TS 内核（L1）里；一层薄适配层（L2）把它接到 pi 的官方 Hook 上；CLI 和 Web 只是两个壳（L3），共享同一份会话 JSONL——改基座只改内核，两壳不动。

§2.3 Web 壳

Web 壳完全自建薄壳：不 fork pi-web、不部署原版作调试台。壳的职责收窄为「读会话 JSONL → 渲染 presentation 纯数据 → 写回 approval_response」，判断全在 L1，壳零领域判断；通用渲染器终端与 Web 共用同一份数据（D8 后续拍板）。

§3 架构 · 一核两壳

四层分层：L0 上游 pi（fork 基线，改动只限品牌/发行层）→ L1 领域内核（零 pi 依赖、零 UI 依赖，纯单测毫秒级）→ L2 pi 适配层 HarnessAdapter（只有这层 import pi，恰好 6 个动作不预留）→ L3 双壳（只读会话条目，不得包含任何领域判断）。

  • DecisionPort：闸门绝不直接调 ctx.ui，只认 ask(req) → Decision；CLI 与 Web 两个实现，行为规则只有一份
  • presentation 是数据：条目 payload 自带纯数据 presentation，两壳各写一个通用渲染器，新增条目类型两壳零改动
  • 单 writer：一个 session 同一时刻只有一个 writer；Web 想「写」就 fork 出自己的分支
  • 唯一真相：sessions/*.jsonl 是全部状态载体，不引入数据库

分层健康的单一标准：删掉 Web 壳，CLI 什么也不少；删掉 CLI 壳，Web 什么也不少。

§4 旧部署方案

使用 PM2 进程守护 Next.js 进程，Nginx 做反向代理与静态资源分发；发布走手工清单：拉取代码 → npm run build → pm2 reload → 验证健康检查端点；回滚保留上一构建目录，切换软链完成。共 15 行流程与脚本（v4 提案整段删除，理由 D2：产物止于设计包 + 原型，部署走 v2.2 交接契约——回滚后本段恢复显示）。
