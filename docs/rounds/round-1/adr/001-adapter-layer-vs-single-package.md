# ADR-001 · 「翻译官」之争：L1/L2 分层 vs 单 pi 包

> **状态：已裁决 · 选 B（单包 + 文件夹边界，无显式翻译官）**——用户 2026-08-17 拍板：「选择方案 B 吧，既然其他开发者也是这样做的，我们就没必要自造可能会遇到很多未知问题。」
> 裁决依据：生态实证（四包解剖，见三.五节）+ 用户直觉。原定「实测后裁决」提前至生态证据充分时。

## 一、问答链（用户五问，原话要点 + 回答要点）

### 问 1：为什么不直接 clone pi 源码，把三服务升级成 package 直接测可用？纯 TS 怎么测试？

- **回答**：纯 TS 测试 = 内存临时目录 + 断言（例：造产物 + 挂提案 → 调回滚 → 断言被拒且版本链不动），毫秒级；三十多组守卫/冲突断言若靠真模型会话验证，一轮几分钟且 LLM 非确定。「直接测可用」也真实存在——测试是三层金字塔：L1 纯单测 / L2 stub 模型集成 / L3 真机 E2E（spike 与收官卡）。
- **clone 的账**：pi 扩展层开发用 npm 包（官方公开 API）全覆盖，clone 买不到测试能力，只买到 fork 维护负担 + 诱惑改内核（D1 红线）；fork 挪到发行轨（T1 出口后，只做品牌层时才需要源码在手）。

### 问 2：适配器是什么东西？（说人话版）

- **回答**：转换插头。L1 领域内核故意不认识 pi，只说「我需要六种能力」（起会话/发消息/注册工具/读会话流/派子 Agent/取上下文用量）；适配器把这六句翻译成 pi 官方调用（如「写一条回滚审计」→ `pi.appendEntry("artifact_rollback", …)`）。全部领域逻辑住 L1，翻译官恰好六个动作不许加第七个。
- **三层好处**：L1 测试不装 pi 不联网（177 条毫秒级）；pi 升级只改翻译官；全仓只有 pi-ext 允许 import pi，红线变 typecheck 可查。

### 问 3：不能直接把功能写入 package？说明功能并没有原生写入 pi？

- **回答**：对——pi 原生只有通用 agent 能力（会话/工具/事件/拦截点），「受管文档、提案、逐块确认、版本链」是本项目独有语义，任何内核都不可能有。D1 实证结论原话：「pi 给你的不是规格，是已交付的挂载点清单」。pi = 毛坯房（水电接口留好），本功能 = 装修，不能砸承重墙（改内核）。

### 问 4：我的目的是新增 pi 的 package 使 pi 有这些能力，不是要翻译官——徒增烦恼制造复杂。

- **回答**：目标与现状不冲突——`pi-ext` **就是**那个 pi package（`pi install @pgoone/next-step-pi` 装完，pi 会话即得六工具 + 闸门）；core 不是要另装的包，是 pi-ext 的**内部 npm 依赖**（pi 官方支持扩展带依赖，安装者无感）。「翻译官」不是运行时中转（纳秒级函数跳转），只是包内代码分两个文件夹。
- **单包合并的代价**：推倒已验收六卡（177 测试 + 六份 verifier 报告）、违反正本 F5（旧仓「领域长在壳里」病根）、pi 升级时业务与接线一起翻。

### 问 5：A/B 之选（lead 提出，用户选择第三条路）

- **A（维持现状）**：对外一个 pi package，内部 core/pi-ext 两文件夹，零返工
- **B（合并单包单目录）**：代码一行不废只挪窝（见下节结构），代价 ≈ 目录重组 + 配置重指 + 文档路径更新（约半天机械工作）
- **用户裁决**：**一阶段跑完、亲自实测后再定 A/B**（本文档即为该决策的挂起记录）

## 二、两方案对照

| 维度 | A · 现状（core + pi-ext 两包） | B · 合并单包 |
|---|---|---|
| 用户安装体验 | `pi install @pgoone/next-step-pi`（core 作为依赖自动带上，无感） | 同左（完全一致） |
| 包内结构 | 领域（core）/接线（pi-ext）分居两包 | 单包内 `src/domain` + `src/adapter` + `src/ports` 文件夹 |
| 领域测试 | 独立包独立跑，177 条毫秒级，无 pi 安装 | 同样可跑（文件夹边界），但包依赖整体安装（测试环境带 pi） |
| 正本 F5 红线 | 完全符合 | 需修订正本（F5 语义从「包边界」改为「文件夹边界」） |
| pi 升级影响面 | 只改 pi-ext 包 | 同一包内 adapter 文件夹（等价） |
| 切换成本 | — | 代码零废，挪文件 + tsconfig/vitest 重指 + 验收文档路径更新 ≈ 半天 |

## 三点五、生态实证（2026-08-17 补，用户要求解剖 pi.dev/packages 复杂项目）

下载解剖四个最复杂包（npm tarball 源码级分析）：

| 包 | 规模 | 形态 | pi import 分布 |
|---|---|---|---|
| pi-hermes-memory（732 tests） | 52 文件 | 单包 | `src/store/`（18 文件）**零 pi import**，handlers/tools 才接线——事实分层 |
| @quintinshaw/pi-dynamic-workflows | 103 文件 | 单包 | 33 个接线文件，**70 个核心逻辑文件不碰 pi**——事实分层 |
| pi-subagents | 188 文件 | 单包 | 61/188 直接 import pi（33%），分层最松，无接口抽象 |
| pi-mcp-adapter（454K/月） | 58 文件 | 单包扁平 | 本身是外部协议翻译器，内部不分层 |

**结论**：①生态 0/4 用「接口包+适配包」两包架构——A 形态比生态重；②但最复杂的两包（hermes/workflows）自发形成**单包内文件夹级分层**（逻辑文件夹零 pi import）= B 方案形态，hermes 732 测试单包内跑证明可测性不牺牲；③单 package 是 pi 生态主流，用户直觉有生态背书。**该证据加强 B 的理由**；A 独有剩余优势仅「core 可独立发布」（本项目不需要）。

## 四、裁决结论与执行（2026-08-17 用户拍板 B）

**结论**：合并单包（`packages/next-step-pi`），**删除显式翻译官接口**（HarnessAdapter L1 契约文件废除）；保留生态共识的软纪律——`src/domain/` 零 pi import（hermes 同款，靠目录约定 + code review，不靠接口强制）。接线代码保留为普通工具模块（谁用谁 import），非接口实现。

**用户第二问的裁定**：「其他开发者没有翻译官 → pi 不会轻易改 API」——方向采纳（生态 5386 包集体直接调 API），严谨补充：pi 处 0.x 版本无永不变更保证，本项目的保险 = **pin 0.84.2 + 升级走显式回归**（正本既有纪律），不靠接口层。

**执行清单**：
1. 物理合并 `packages/core` + `packages/pi-ext` → `packages/next-step-pi`（src/domain | src/pi | src/ports）
2. 删除 `core/src/adapter/harness-adapter.ts` 接口文件与 barrel 中的契约导出（实现文件保留为普通模块）
3. tsconfig/vitest/workspace 配置重指；177+16 测试全绿复跑
4. 正本 F5 修订：解耦语义从「包边界」改「文件夹边界」；ROADMAP 三服务→Package 节同步
5. 时点：T1-07 verifier 结果出来并 commit 后立即执行（重组为独立 commit + 快速复验），不影响 T1-08 起后续卡
