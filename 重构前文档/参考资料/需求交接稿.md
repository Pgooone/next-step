## 1. 项目是什么

<aside>
🎯

**一句话**：Next-Step v2.0 是一条本地多 Agent 产线，把「一句想法」变成「可动工的设计包 + 可评审的原型」。产线每一步的产物都受管、可逐块签字、可追溯到上游；成品出缺陷时能沿追溯链归因到具体阶段，改完只重跑下游；跑顺过的队伍与经验沉淀成可复用的**配方**与**技能**。

</aside>

**使命**：让一个人用一队 AI，稳定产出**别人敢接手动工**的设计包与原型——过程全程可见、每步可签字、出错可归因、经验可复用。

**版本边界**（范围纪律：重构与扩范围不能同时做）

| 里程碑 | 完成的定义 | 含 |
| --- | --- | --- |

## 2. 为什么要重构：三条机制性缺失

<aside>
⚠️

漂移的根因不是「功能加多了」。**如果只重写代码不补这三条，v2.0 会以更快的速度漂移第二次。**

</aside>

| # | 问题 | 本期对策 |
| --- | --- | --- |
| **P1** | 没有主干判据，所以任何功能都能被论证「有用」。缺的不是克制，是**尺子** | 确立三根柱子：**产能 / 可控 / 可追溯返工**。新功能必须写明落在哪根柱子 + 让哪条 AC 从红变绿 |
| **P2** | 概念膨胀，六个近义词各做一半：`Agent 档案` / `agent 模板` / `skill` / `pipeline 蓝图` / `队伍模板` / `主脑 plan` | 见 §5 最小对象模型，六个概念压成两个可复用资产 |
| **P3** | 没有追溯链，所以「缺陷归因」在物理上不可能。需要三个前提（阶段间追溯链 / 可判定验收标准 / 缺陷→阶段归因判据），目前**一个都没有** | M2 补最小追溯链（块级 `sourceRef`）。**这是 v2.0 唯一真正的新地基** |

🔴 **关于 P3 的一个常见误读**：旧稿把这条写成「agent 断点续跑」，但「从阶段重跑」已交付——那是**人来定位、系统重跑**。真正要的是**系统来定位**。前者是编排问题（已解决），后者是追溯问题（未解决）。不要把两者混为一谈。

## 4. 技术地基（已完成调研，不需重新评估）

<aside>
🧱

**地基结论**：以 **pi 的 SDK / 扩展 API** 为承重墙；pi-web 降为**可替换的表现层**；**不迁 dsh**。下面的事实均已核实，请直接引用，不要重开调研。

</aside>

### 4.1 pi 已核实的原生能力

**事件顺序（一次 run）**

```
input → before_agent_start → agent_start → message_start/update/end
      → turn_start → context → before_provider_headers/request
      → after_provider_response
      → tool_execution_start → tool_call → tool_execution_update
      → tool_result → tool_execution_end
      → turn_end → agent_end → agent_settled
```

- `tool_call`：可返回 `{ block: true, reason }` 拦住工具，也可改写 `event.input`
- `tool_result`：可改写结果，多个扩展形成 middleware 链
- 状态机：`Idle → Streaming → ExecutingTools → Settling → Idle`；工具返回 `{ terminate: true }` 可跳过再次请求 LLM 直接收尾

**扩展 API**

| API | 用途 |
| --- | --- |
| `pi.registerTool()` | 注册领域工具 |
| `pi.registerCommand()` | 注册斜杠命令 |
| `pi.appendEntry()` | 写自定义会话条目，**持久化但不进 LLM 上下文** |
| `pi.registerEntryRenderer()` | 自定义条目的**终端**渲染（注：不影响 Web 前端） |
| `ctx.ui.select/confirm/input/notify` | 终端交互 |
| `ctx.sessionManager.getEntries/getBranch/buildContextEntries/getLeafId` | 读会话流 |

**SDK（当库嵌入）**

| API | 用途 |
| --- | --- |
| `createAgentSession()` | 起一个会话 |
| `session.prompt/steer/followUp/subscribe/navigateTree/compact/abort/dispose` | 驱动与订阅 |
| `createAgentSessionRuntime()` | 多会话管理：`newSession/switchSession/fork/importFromJsonl` |
| `SessionManager.inMemory()/create()` | 会话存储（测试用 inMemory） |
| `tools` 白名单 / `excludeTools` / `noTools: "all"\ | "builtin"` |
| 内置 `edit` 工具返回 `details.patch` | 标准 unified patch，专给 SDK 消费者 |
| `pi --mode rpc` | LF 分隔 JSONL，供外部前端驱动 |

**文件布局与环境变量**

- `~/.pi/agent/`：`extensions/`、`skills/`、`prompts/`、`settings.json`、`models.json`、`sessions/*.jsonl`
- 项目级扩展：`.pi/extensions/`（开发用，改完新起会话即生效）
- `PI_CODING_AGENT_DIR`（换目录，开发沙盒用）、`PI_SESSION_ID`、`PI_SESSION_FILE`、`PI_PROVIDER`、`PI_MODEL`、`PI_REASONING_LEVEL`、`PI_OFFLINE`
- 会话树：`id → parentId`，命令 `/tree`；分支用 `fork(entryId, { position: "at" })`

**pi 刻意不内置、但有官方 example 可参照**：sub-agents（`examples/extensions/subagent`）、plan mode（`plan-mode`）、权限门（`permission-gate.ts`、`protected-paths.ts`、`sandbox`）。

### 4.2 pi-web 的能力与短板

**现成能力**：会话工作区（context usage / cost / compaction）、两种分支（New session / Edit from here）、文件浏览 + Git diff、worktree 切换、Web 配置面板、中英双语 UI。读 `~/.pi/agent`，端口 30141，`npx @agegr/pi-web@latest`。

<aside>
🚧

**决定性短板**：pi-web **没有插件机制、没有 UI 槽位**。对外唯一扩展点是浏览器事件 `pi-web:session-row-contextmenu`。想加 UI 只能改 React 组件树。叠加它几乎是单人项目（MIT / Next.js / 4.4k stars / 531 commits / 主维护者 411 contributions）——**把领域层写进它的组件里 = 变相 fork = 违反 F4**。

</aside>

### 4.3 为何不迁 dsh（N2 的依据，不要重新讨论）

dsh 架构确实更彻底（Cordis 内核、`tools/pre-execute` 带「询问」态、`dsh-approval` 审批即服务、现成 `ui-trajectory`），但：

- v0.1 developer preview（npm `0.1.0-rc.6`）2026-08-13 发布，README 全大写声明 **THERE WILL BE COMPATIBILITY-BREAKING CHANGES**
- `dsh web` 暴露 60+ RPC 方法，仅 Host header 检查、**无 auth**（Discussion #853，无维护者回应，无 [SECURITY.md](http://SECURITY.md)）
- 插件无签名、无权限清单；`danger-full-access` 有用户家目录被删案例（issue #461）
- **不接受外部 PR**，与 F4 精神冲突
- 真实学习成本是 Cordis 元框架（Service/Provider/Consumer、`group`+`isolate`、`cordis.yml` 的 `insert`/`!!js`/profile 分层）

✅ **从 dsh 只借两条设计**（不迁实现）：① append-only 会话日志、按来源可检视；② approval 作为一等服务。

### 4.4 分层架构：一核两壳

| 层 | 里面放什么 | 依赖约束 | 怎么测 |
| --- | --- | --- | --- |
| **L0** 上游 pi | agent loop、会话树、内置工具 | **不改**，pin 版本 | — |
| **L1** 领域内核 | diff 解析、`sourceRef` 血缘图、提案状态机、重试策略、doc/coding 模式规则、闸门判定、归因算法 | **零 pi 依赖、零 UI 依赖**，纯 TS | 纯单测，不需模型不需界面 |
| **L2** pi 适配层 = `HarnessAdapter` | `registerTool` / `registerCommand` / `tool_call` 拦截 / `tool_result` 改写 / `appendEntry` / 事件订阅 | **只有这层 import pi** | `SessionManager.inMemory()`  • `createAgentSession()`，stub 掉模型 |
| **L3** 两个壳 | CLI 壳 = pi 本体；Web 壳 = pi-web 或自建薄壳 | 只读会话条目；**不得包含任何领域判断** | 手动 / E2E |

**分层健康的单一标准**：删掉 Web 壳，CLI 应该什么都不少；删掉 CLI 壳，Web 应该什么都不少。

`HarnessAdapter` 只覆盖 6 个真实用到的动作，**不预留**：起会话 / 发消息 / 注册工具 / 读会话流 / 派子 Agent / 取上下文用量。

### 4.5 双前端三条强制规约

| 规约 | 内容 | 为什么 |
| --- | --- | --- |
| **交互端口 `DecisionPort`** | 闸门**绝不直接调 `ctx.ui`**。L1 只依赖 `DecisionPort.ask(req) → Decision`。L2 提供两个实现：`CliDecisionPort`（`ctx.ui.select/confirm/input`）、`EntryDecisionPort`（`appendEntry({ type: "approval_request", status: "pending" })` → 等 `approval_response` 条目） | 否则会写两套 F1，且行为永远对不齐。副作用是正面的：每条裁决都落入 append-only 日志，M2/M6 直接复用 |
| **presentation 是数据，不是代码** | 自定义条目 payload 自带纯数据 presentation（`title` / `badges` / `rows` / `diffRef`），两个前端各写一个**通用渲染器** | `registerEntryRenderer()` 只影响终端，Web 不认识自定义条目。这条保证新增条目类型时两个前端都不用改，且回放与直播一致 |
| **单 writer** | 一个 session 同一时刻只有一个 writer。Web 想「写」就 `fork(entryId, { position: "at" })` 出自己的分支 | CLI 与 Web 双写会互相踩。不要为双写引入数据库（破 F3）；与 N8 一致 |

### 4.6 唯一真相：会话 JSONL

`~/.pi/agent/sessions/*.jsonl` 是全部状态载体。CLI 跑的会话 Web 能回放；Web fork 的分支 CLI `/tree` 能看到；`appendEntry` 的自定义条目也在同一文件。不引入数据库（F3）。

## 5. 最小对象模型（四实体 + 两资产，除此之外不新增名词）

| 对象 | 定义 | 落盘 |
| --- | --- | --- |
| **Project** | 一个工作区 = 一个目录 | 项目根 |
| **Stage** | 产线上的一步：谁做、做什么、验收标准、依赖谁 | run 内 |
| **Agent** | 可持久化档案：角色 + 模型 + 技能 + 工具 + 模式 + 思考强度 | `.pi/agents/` |
| **Artifact** | 受管产物：内容 + 版本链 + 块级来源引用 + 归属 stage | `.pi/artifacts/` |
| **Recipe（配方）** | 可复用产线：有序 Stage + 每步队员（池挑 ∪ 内联规格）+ 验收标准 + 执行模式 | `.pi/recipes/` |
| **Skill** | 可复用做法：给 Agent 加载的过程性知识，带版本 | `.pi/skills/` |

**旧概念映射（这就是减法本身）**

| 旧概念 | 归入 | 说明 |
| --- | --- | --- |
| pipeline 蓝图 | **Recipe** | 蓝图 = 只含池挑、无验收的 Recipe 子集 |
| 队伍模板 | **Recipe** | 二者本就是同一形状的超集/子集 |
| 主脑 plan | **Recipe（未落盘的一次性实例）** | AI 拟的 Recipe，确认后可另存 |
| agent 模板 / 导入导出 | **Agent 的序列化格式** | 不是新对象 |
| 工作流 | 删除 | 与 Recipe 完全重复 |
| preset | 删除 | dsh 的词，不引入 |

⚠️ **写需求时禁用「包括且不限于」这五个字**——它是把猜测写进合同。例：旧稿「一键构建持久化 agents，来源包括且不限于 skills、工作流或其他」已拆为两条可断言操作：**从 Skill 派生 Agent**、**从 Recipe 的某个 Stage 提取 Agent**。

## 6. 范围：M1–M6 与全部验收标准

### M1 · 受管产物与「diff 工具化」

**沿用（不重做）**：`artifact-service`、`pending-change-service`、`lcs.ts`、块级绿/红/黄高亮、逐块 ✓/✗、版本链、回滚、外部手改检测、`ArtifactPanel`。

> 旧稿的文档工具 1–3 约 90% 已交付。**正确动作是迁移，不是重写。**
> 

**真新增只有一条**：把 diff 从「人看的 UI」变成「**Agent 可读的工具返回值**」。

- `get_artifact_diff(artifactId, fromVersion, toVersion)` → 结构化变更块列表（含 `sourceRef`）
- `list_my_artifacts()` → 当前 Agent 名下产物 + 各自当前版本 + 最近改动摘要
- `get_artifact_history(artifactId)` → 版本链 + 每版由哪个 stage/agent 产生

| AC | 内容 |
| --- | --- |
| **AC-1.1** | 任一 doc 模式 Agent 可在会话中调用三个只读工具并拿到结构化结果，无需人工粘贴 |
| **AC-1.2** | Agent 调用 `get_artifact_diff` 后能正确说出「上一版改了哪几块」，与 UI 显示的块数一致 |
| **AC-1.3** | doc 模式 Agent 的工具集中**不存在** write/edit；任何写入尝试只能经 `propose_edit` |
| **AC-1.4** | 三个新工具为**只读**，不产生 PendingChange |

🔧 **pi 落点**：`registerTool` 注册三工具；内置 `edit` 的 `details.patch` 直接用，不自己解析 diff 文本；AC-1.3 用 `tools` 白名单 / `excludeTools` **从能力层面物理禁用**，不靠 prompt 约束。

### M2 · 追溯链与缺陷归因 🔴 本期唯一新地基

**新增**

- 产物块携带 `sourceRef: { artifactId, version, blockAnchor }[]`
- Stage 定义中「验收标准」升为**必填结构化字段**（每条可断言）
- 归因工具 `trace_defect(artifactId, blockAnchor | 自然语言描述)` → 该块上游链条 + 每一环验收标准 + **最早偏离点候选**（带置信度与依据）

| AC | 内容 |
| --- | --- |
| **AC-2.1** | 原型产物任一块可回溯到详细设计的具体段落，再回溯到需求的具体条目（**三跳可达**） |
| **AC-2.2** | 给定一句「原型缺少深色模式」，`trace_defect` 能定位到「详细设计 v1 未覆盖需求 #Y」，并给出 file/anchor 级证据 |
| **AC-2.3** | 若追溯链中断（某块无 `sourceRef`），归因结果必须**显式报告断链位置**，不得猜测 |
| **AC-2.4** | 归因只输出**判断与依据**，不自动改任何产物 |

🔧 **pi 落点**：`sourceRef` 存在 `appendEntry()` 自定义条目（持久化但**不进 LLM 上下文**，避开上下文爆炸风险）；`sourceRef` **由工具写入而非模型输出**；归因走轻读（元数据 + 按需取）。

### M3 · Agent 与配方

**沿用**：`agent-profile-store`（已支持 model / skills / tools / thinkingLevel）、`AgentManager`、doc/coding 模式、`pipeline-store`、`team-template-store`。

**新增**

- 两个存储合并为统一 `recipe-store`（迁移旧数据，**不并存**）
- Agent 序列化：单个导出/导入（JSON，**含技能引用而非技能副本**）
- 从 Skill 派生 Agent；从 Recipe 某个 Stage 提取 Agent 存入池
- Agent 档案变更走与产物同一条确认通道（前提：D3 采纳甲）

| AC | 内容 |
| --- | --- |
| **AC-3.1** | 导出的 Agent 在清空本地后可完整导入，跑出同样行为（模型不可用时**明确报错，不静默降级**） |
| **AC-3.2** | 旧 `pipeline.json` 与旧队伍模板一次性迁移为 Recipe，迁移后旧路径不再被读取 |
| **AC-3.3** | 改 Agent 档案产生一条待确认变更，确认后生成新版本，可回滚 |

### M4 · 编排与断点续跑

**沿用**：`mastermind-orchestrator`（计划闸、失败暂停给选项、上游累积喂下游）、从阶段重跑与 run 血缘、运行历史面板。

**新增**

- Stage 从「一次性对象」升为「引用 Recipe 中的一步」，便于跨 run 对齐同一步
- 重跑入口增加**归因驱动**路径：`trace_defect` 结果可一键「从这一步重跑」

| AC | 内容 |
| --- | --- |
| **AC-4.1** | 从归因结果一键重跑，`<K` 阶段复用已确认产物的最新版本，`≥K` 阶段重新生产 |
| **AC-4.2** | 源 run 只读、深拷；新旧 run 在历史面板并列且血缘可见；刷新后仍在 |
| **AC-4.3** | 上游有未确认的待确认变更时，重跑必须**拒绝启动并说明原因** |

🔧 **pi 落点**：会话树 `id → parentId` + `fork(entryId, { position: "at" })` / `importFromJsonl()`——**不要自己设计版本模型**。

### M5 · 经验沉淀（提案制自进化）· **v2.1，本期不开工**

**新增**

- 会话结束后的**沉淀提案**：把反复出现的做法抽象为 Skill 提案（新建或 patch）
- Skill 带语义版本 + 变更说明 + 来源会话链接

- 加载外部 Skill 前做提示注入静态扫描，命中即拒绝加载并报告命中项

| AC | 内容 |
| --- | --- |
| **AC-5.1** | Skill 提案以待确认变更呈现，逐块确认后才落盘并产生新版本 |
| **AC-5.2** | 任一 Skill 可回滚到任意历史版本；回滚本身也是一次新版本 |
| **AC-5.3** | 系统**永不**在无人确认的情况下修改 Skill 或 Agent 档案（红线自检项） |
| **AC-5.4** | 含已知注入模式的 Skill 文件被拒绝加载，并在 UI 明示命中规则 |
