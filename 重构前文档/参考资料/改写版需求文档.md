**使命**：让一个人用一队 AI，稳定产出**别人敢接手动工**的设计包与原型——过程全程可见、每步可签字、出错可归因、经验可复用。

### 0.1 阅读约定（写给执行本次重构的人与 AI）

- **本文自包含。** 执行重构不需要预读 V1.1 / V1.2 的历史文档；一切仍然生效的历史前提，全部收在 §0.2。

## 1. 本次重构要解决的真问题

漂移的根因不是「功能加多了」，是三条机制性缺失。**如果只重写代码不补这三条，v2.0 会以更快的速度漂移第二次。**

### P1 · 没有主干判据，所以任何功能都能被论证「有用」

十三轮里每一条新功能都有合理的理由，但没有任何一条判据能说「这条不该做」。缺的不是克制，是**尺子**。

> **本期对策**：确立三根柱子（产能 / 可控 / 可追溯返工），任何新功能必须写明落在哪根柱子上、以及它让哪条 AC 从红变绿。写不出来的，不做。
> 

### P2 · 概念膨胀，六个近义词各做一半

`Agent 档案` / `agent 模板` / `skill` / `pipeline 蓝图` / `队伍模板` / `主脑 plan` —— 第十三轮需求文档自己承认「与既有三大能力高度重叠，新意在错位」。**功能重叠是漂移的病征，不是创新。**

> **本期对策**：见 §3 最小对象模型，六个概念压成两个可复用资产。
> 

### P3 · 没有追溯链，所以「缺陷归因」在物理上不可能

草稿里最有价值的一条是「我说原型有缺陷，你去找是哪个 agent 阶段出的问题」。但这件事需要三个前提，目前**一个都没有**：

1. 阶段间的可追溯链（原型这个按钮 ← 详细设计 §X ← 需求 #Y）——**V1.2 明确砍掉了 RTM 需求追溯矩阵，砍掉的正是它的地基**
2. 每个产物有可判定的验收标准（否则「有缺陷」无法与产物机械对齐）
3. 缺陷 → 阶段的归因判据（需求没写？设计漏了？原型实现错？）

> **本期对策**：M2 补最小追溯链（块级 `sourceRef`）。这是 v2.0 唯一真正的新地基。
>

## 3. 最小对象模型（概念减法）

**四个实体 + 两个可复用资产。除此以外不新增名词。**

| 对象 | 定义 | 落盘 |
| --- | --- | --- |
| **Project** | 一个工作区 = 一个目录 | 项目根 |
| **Stage** | 产线上的一步：谁做、做什么、验收标准、依赖谁 | run 内 |
| **Agent** | 一份可持久化档案：角色 + 模型 + 技能 + 工具 + 模式 + 思考强度 | `.pi/agents/` |
| **Artifact** | 一份受管产物：内容 + 版本链 + 块级来源引用 + 归属 stage | `.pi/artifacts/` |
| **Recipe（配方）** | 可复用的产线：有序 Stage + 每步队员（池挑∪内联规格）+ 验收标准 + 执行模式 | `.pi/recipes/` |
| **Skill** | 可复用的做法：给 Agent 加载的过程性知识，带版本 | `.pi/skills/` |

### 旧概念映射（这就是减法本身）

| 旧概念 | 归入 | 说明 |
| --- | --- | --- |
| pipeline 蓝图（第七轮） | **Recipe** | 蓝图 = 只含池挑、无验收的 Recipe 子集 |
| 队伍模板（第十三轮） | **Recipe** | 二者本就是同一形状的超集/子集 |
| 主脑 plan（第 8.6 轮） | **Recipe（未落盘的一次性实例）** | AI 拟的 Recipe，确认后可另存 |
| agent 模板 / 导入导出 | **Agent 的序列化格式** | 不是新对象，是 Agent 的一种表示 |
| 工作流 | 删除 | 与 Recipe 完全重复 |
| preset | 删除 | dsh 的词，不引入 |

<aside>
✅

**收益**：草稿里「一键构建持久化 agents，来源包括且不限于 skills、工作流或其他」这条无法验收的需求，在新模型下变成两条可断言的操作：**从 Skill 派生 Agent**、**从 Recipe 的某个 Stage 提取 Agent**。「包括且不限于」这五个字必须从需求文档里消失——它是把猜测写进合同。

</aside>

## 4. 待拍板决策（lead 已列候选与推荐，请逐条拍板）

### D1 · 地基怎么选（最重要，决定后面 90% 的工作）

草稿同时提了三条互斥的路：留在 pi-web、参考 dsh、自建 web 端。**这三条不是可以「都参考」的。**

| 选项 | 代价 | 风险 |
| --- | --- | --- |
| 甲 · 留在 pi-web 叠领域层（现状） | 最低 | 上游 UI 约束、你的 `lib/domain` 事实上已成「特权核心」，与插件化理念相悖 |
| 乙 · 迁到 dsh 做插件 | 高：Cordis + pnpm 生态、全部重写 | dsh 2026-08-13 才发布 developer preview，官方声明会破坏兼容 |
| 丙 · 自建 web 端 | 最高：等于再造 pi-web | 把精力花在你没有差异化的那一层 |

**推荐：甲 + 一道适配器边界，把「选地基」变成「不必现在选」。**

定义 `HarnessAdapter` 接口（起会话 / 发消息 / 注册工具 / 读会话流 / 派子 Agent / 取上下文用量），领域层只依赖它。现在实现 pi 版；dsh 稳定后加一个 dsh 版即可切换。

> 这才是从 dsh 学到的正确东西：**不是搬去 dsh，是学会用插件边界思考**。dsh 真正值得抄的两点是「append-only 会话日志 + 按来源可检视的 Trajectory 视图」和「approval 作为一等服务」——这两点都可以在甲方案里实现，不需要换地基。
> 

### D2 · 产物边界到哪

| 选项 | 说明 |
| --- | --- |
| 甲 · 止于设计包 + 原型（**推荐**） | 「可上线」靠 v2.2 的交接契约：产出物能被外部编码 Agent 零翻译消费 |
| 乙 · 一路做到部署上线 | 需要代码库管理、测试、CI、环境、密钥、回滚、观测——另一个数量级，且直接推翻 F3 |

### D3 · 自进化做到什么强度

Hermes 的闭环是「执行 → 记录经验 → 抽象成 Skill → 用中改进 → Curator 按使用率归档 → 安全扫描」。直接照搬有**两个致命问题**：

1. **燃料缺失**：自进化的燃料是「好坏信号」。你现在没有任何自动评测——第 8.6 轮需求文档自己写了「大脑拆活质量 LLM 非确定性、难自动测」，只能靠 sf-mini 人肉当 oracle。**没有评测信号的自进化 = 有方向感的随机漂移**，而且是**静默的**。
2. **红线冲突**：你最强的主张是「AI 不能悄悄改东西」。自进化 = AI 悄悄改 Skill 和 Agent。**照搬就是自己破自己的立国之本。**

| 选项 | 说明 |
| --- | --- |
| 甲 · 提案制（**强烈推荐**） | 自进化只产出**提案**（新建 Skill / patch 现有 Skill / 改 Agent 档案），走**与文档完全同一条**「提案 → 逐块确认 → 新版本」通道 |
| 乙 · 自动写入 + 事后审计 | 破 F1；且无评测信号，审计等于人肉复查全部改动，比确认更累 |
| 丙 · 参数/代码级进化 | 明确不做（N4） |

<aside>
💡

**甲方案的额外收益（这是本次重构最大的架构简化）**：自进化不是新机制，而是你已有的块级确认机制的**第四类客户**——第一类文档、第二类 Agent 档案、第三类 Recipe、第四类 Skill。四类共用一套 `propose → PendingChange → 逐块确认 → 版本 → 回滚`。工作量降一个数量级，同时把「六套 UI」收敛成一套。

</aside>

### D4 · 追溯粒度

| 选项 | 说明 |
| --- | --- |
| 甲 · 块级 `sourceRef`（**推荐**） | 产物每个块记录上游来源（artifactId + 版本 + 块锚点）。够支撑缺陷归因，成本可控 |
| 乙 · 完整 RTM 矩阵 | V1.2 已否决过一次，理由仍成立 |
| 丙 · 只记 stage 级归属 | 太粗，归因只能定位到「设计阶段」，不能定位到「设计漏了深色模式这一条」 |

### D5 · 是否接受 §3 的概念收敛（六并二）

推荐接受。不接受的话，请指出哪两个概念确实不能合并，以及区分它们的**用户可感知差异**是什么。

## 5. 模块需求与验收标准

### M1 · 受管产物与「diff 工具化」

**沿用（不重做）**：`artifact-service`、`pending-change-service`、`lcs.ts`、块级绿/红/黄高亮、逐块 ✓/✗、版本链、回滚、外部手改检测、`ArtifactPanel`。

> 草稿的文档工具 1–3 有约 90% 是 V1.1 第一~四轮已交付的能力。**这里的正确动作是迁移，不是重写。** 这三个服务是你唯一被二十轮验证过的资产。
> 

**真新增只有一条**：把 diff 从「人看的 UI」变成「**Agent 可读的工具返回值**」。

- `get_artifact_diff(artifactId, fromVersion, toVersion)` → 结构化变更块列表（含 `sourceRef`）
- `list_my_artifacts()` → 当前 Agent 名下产物 + 各自当前版本 + 最近改动摘要
- `get_artifact_history(artifactId)` → 版本链 + 每版由哪个 stage/agent 产生

**AC**

- AC-1.1 任一 doc 模式 Agent 可在会话中调用三个只读工具并拿到结构化结果，无需人工粘贴
- AC-1.2 Agent 调用 `get_artifact_diff` 后能在回复中正确说出「上一版改了哪几块」，与 UI 显示的块数一致
- AC-1.3 doc 模式 Agent 的工具集中**不存在** write/edit；任何写入尝试只能经 `propose_edit`
- AC-1.4 三个新工具为**只读**，不产生 PendingChange

### M2 · 追溯链与缺陷归因 🔴 本期唯一新地基

**新增**

- 产物块携带 `sourceRef: { artifactId, version, blockAnchor }[]`
- Stage 定义中「验收标准」升为必填结构化字段（每条可断言）
- 归因工具 `trace_defect(artifactId, blockAnchor | 自然语言描述)` → 返回该块的上游链条 + 每一环的验收标准 + **最早偏离点候选**（带置信度与依据）

**AC**

- AC-2.1 原型产物任一块可回溯到详细设计的具体段落，再回溯到需求的具体条目（三跳可达）
- AC-2.2 给定一句「原型缺少深色模式」，`trace_defect` 能定位到「详细设计 v1 未覆盖需求 #Y」，并给出 file/anchor 级证据
- AC-2.3 若追溯链中断（某块无 `sourceRef`），归因结果必须**显式报告断链位置**，不得猜测
- AC-2.4 归因只输出**判断与依据**，不自动改任何产物

<aside>
🔴

草稿把这条写成「agent 断点续跑」，但第十二轮已经交付了「从阶段重跑」——那是**人来定位、系统重跑**。草稿真正想要的是**系统来定位**。这是两个完全不同的功能，前者是编排问题（已解决），后者是追溯问题（未解决）。这条是整份草稿里最有价值、却被写得最轻的一条。

</aside>

### M3 · Agent 与配方

**沿用**：`agent-profile-store`（已支持 model / skills / tools / thinkingLevel）、`AgentManager`、doc/coding 模式、`pipeline-store`、`team-template-store`。

**新增**

- 两个存储合并为统一 `recipe-store`（迁移旧数据，不并存）
- Agent 序列化：单个导出/导入（JSON，含技能引用而非技能副本）
- 从 Skill 派生 Agent；从 Recipe 某个 Stage 提取 Agent 存入池
- Agent 档案变更走与产物同一条确认通道（前提：D3 采纳甲方案）

**AC**

- AC-3.1 导出的 Agent 在清空本地后可完整导入，跑出同样行为（模型不可用时明确报错，不静默降级）
- AC-3.2 旧 `pipeline.json` 与旧队伍模板一次性迁移为 Recipe，迁移后旧路径不再被读取
- AC-3.3 改 Agent 档案产生一条待确认变更，确认后生成 Agent 档案的新版本，可回滚

### M4 · 编排与断点续跑

**沿用**：`mastermind-orchestrator`（计划闸、失败暂停给选项、上游累积喂下游）、从阶段重跑与 run 血缘、运行历史面板。

**新增**

- Stage 从「一次性对象」升为「引用 Recipe 中的一步」，便于跨 run 对齐同一步
- 重跑入口增加**归因驱动**路径：`trace_defect` 结果可一键「从这一步重跑」

**AC**

- AC-4.1 从归因结果一键重跑，`<K` 阶段复用已确认产物的最新版本，`≥K` 阶段重新生产
- AC-4.2 源 run 只读、深拷；新旧 run 在历史面板并列且血缘可见；刷新后仍在
- AC-4.3 上游有未确认的待确认变更时，重跑必须**拒绝启动并说明原因**（不得用未签字内容喂下游）

### M5 · 经验沉淀（提案制自进化）· v2.1

**新增**

- 会话结束后的**沉淀提案**：把本次对话中反复出现的做法抽象为 Skill 提案（新建或 patch）
- Skill 带语义版本 + 变更说明 + 来源会话链接
- 使用计数与最近使用时间；久未使用的 Skill 进入「建议归档」列表（**只建议，不自动归档**）
- 加载外部 Skill 前做提示注入静态扫描，命中即拒绝加载并报告命中项

**AC**

- AC-5.1 Skill 提案以待确认变更呈现，逐块确认后才落盘并产生新版本
- AC-5.2 任一 Skill 可回滚到任意历史版本；回滚本身也是一次新版本
- AC-5.3 系统**永不**在无人确认的情况下修改 Skill 或 Agent 档案（红线自检项）
- AC-5.4 含已知注入模式的 Skill 文件被拒绝加载，并在 UI 明示命中规则
