# Next-Step v2.0 · D1 地基选型实证：pi / pi-web / dsh

<aside>
🎯

**一句话结论**：你上传的那段视频讲的不是 dsh，而是 **pi 自己的内核**。它描述的每一项机制（状态机、消息三态、四层事件、工具前后拦截）pi 都已原生具备。所以 D1 建议从「甲」微调为「甲′」——**承重墙下移到 pi 的 SDK / 扩展 API，pi-web 降级为可替换的表现层**，不迁 dsh。

</aside>

## 0. 三问速答

| 问题 | 答案 |
| --- | --- |
| 视频里那套 agent 最基础功能，pi 有吗？ | **全部有，而且是原生的**。视频本身就是 pi 内核源码解析（证据见 §1） |
| dsh 和 pi 谁更简单、更适合 Next-Step？ | **pi 更简单也更贴合**。dsh 抽象更强，但要先学 Cordis 一整套元框架，且当前是 v0.1 developer preview，官方明说会破兼容 |
| 直接改 pi vs 继续改别人做完的 pi-web？ | **不是二选一**。领域逻辑写成 pi 扩展 / 用 pi SDK 起会话（承重墙），UI 才落到 pi-web（表现层）。把领域层长在 pi-web 的 React 组件里，是三条路里最慢也最贵的一条 |

## 1. 先更正一个前提：视频讲的是 pi，不是 dsh

视频封面标题被截断成「（一）DeepSeek Harn...」，容易误认成 dsh 解析。但片中 **05 References** 页写得很清楚：

- 标题：**「（一）pi-agent 从复杂到简单」**
- 引用仓库：`badlogic/pi-mono`（main 分支，checked 2026-08-12）
- 引用文件：`packages/ai/src/types.ts`、`packages/agent/src/types.ts`、`packages/agent/src/agent-loop.ts`
- 出品：卡兵说 bilibili

> 这个更正很重要：它把「我要不要造这套底座」直接变成了「我只要用 pi 已经写好的底座」。
视频里每一张架构图，都是 pi 源码里的既有结构，不是某种理想模型。
> 

### 视频四段内容 ↔ pi 原生对应物

| 视频章节 | 视频讲的内容 | pi 里的原生对应 |
| --- | --- | --- |
| Chat vs Agent | Agent = Memory + Planning + Tools + Action，区别于一问一答 | pi 就是 coding agent 内核，agent loop 原生 |
| **State** | 状态机 `Idle → Streaming → ExecutingTools → Settling → Idle`；`prompt()` 启动一次 run；终止型工具 `result.terminate = true` 时跳过再次请求 LLM 直接收尾；`Settling → Idle` 由 `agent_end` listeners + `finishRun()` 完成，`isStreaming = false` | `session.prompt()` / `steer()` / `followUp()`；`session.isStreaming`；`agent_end` 与 `agent_settled` 两个事件把 Settling→Idle 显式暴露出来；工具返回 `{ terminate: true }` |
| **Message** | UserMessage（输入 / Steering / Follow-up）、AssistantMessage（`content[]` = TextContent / ThinkingContent / ToolCall，带 `stopReason`）、ToolResultMessage 回灌 Context | `session.messages`；`message_start` / `message_update` / `message_end` 事件；`prompt` / `steer` / `followUp` 三个入口正好是视频里 UserMessage 的三种来源 |
| **Event** | 四层事件：Agent Event（一次 run 边界）、Turn Event（一次模型响应 + 完整工具批次）、Message Event、Tool Event；三泳道 STATE / CONVERSATION / EVENTS 对照；Hooks 泳道 `beforeToolCall → allow/block`、`afterToolCall → optional override` | 实际事件顺序：`input → before_agent_start → agent_start → message_* → turn_start → context → before_provider_request → after_provider_response → tool_execution_start → tool_call → tool_execution_update → tool_result → tool_execution_end → turn_end → agent_end → agent_settled` |
| 片尾预告 | 「下一期：Pi 如何管理会话」 | `SessionManager`  • `session.jsonl`；`id → parentId` 形成会话树与分支；`/tree` 命令 |

<aside>
⚠️

**一处命名要对齐**：视频画的是 `beforeToolCall` / `afterToolCall`（概念名）。pi 里的真实事件名是 **`tool_call`**（可 `{ block: true, reason }`，也可改写 `event.input`）和 **`tool_result`**（可改写结果，多个扩展形成 middleware 链）。语义完全一致，只是命名不同——写扩展时按后者写。

</aside>

## 2. 关键结论：视频里的 Hook 点，正好是 Next-Step 红线的挂载点

这不是巧合。需求文档里 F1「提案 → 逐块确认 → 新版本」和 F2「计划闸 + 失败自重试 1 次」这两条红线，本质就是要在「模型想动手」和「真的动手」之间插一层。pi 的 `tool_call` 事件就是这一层，而且是官方支持的、不需要 fork（正好守住 F4「不 fork 上游」）。

| 需求文档里的东西 | pi 原生落点 | 备注 |
| --- | --- | --- |
| **M1** diff 工具化 | `pi.registerTool()` 注册领域工具；内置 `edit` 工具的结果里带 `details.patch`（标准 unified patch，专门给 SDK 消费者用） | 不用自己解析 diff 文本 |
| **M1-AC1.3** doc 模式下不得有 write/edit | SDK 侧 `tools` 白名单 / `excludeTools` / `noTools: "builtin"` | 从能力层面物理禁用，比 prompt 约束可靠 |
| **M2** 追溯链 / **D4** 块级 `sourceRef` | `pi.appendEntry()` 写自定义条目（**持久化但不进 LLM 上下文**）+ `pi.registerEntryRenderer()` 渲染；`tool_call` / `tool_result` 里由工具写入 `sourceRef` | `appendEntry` 是这套需求里最被低估的一颗原语：血缘数据不污染上下文预算 |
| **F1** 逐块确认 | 订阅 `tool_call` → `ctx.ui.confirm()` / `ctx.ui.select()` → 放行或 `{ block: true, reason }` | 官方 examples 里有 `permission-gate.ts`、`protected-paths.ts` 可直接抄 |
| **F2** 计划闸 + 失败自重试 1 次 | `tool_result` 拦截判定失败 → 决定重试或终止；`turn_end` 做批次收口 | 重试计数放扩展自己的状态里 |
| **M4** 重跑 / 血缘 | `SessionManager` 的 JSONL 树（`id → parentId`）+ `AgentSessionRuntime.fork(entryId, { position: "at" })` / `importFromJsonl()` | 「从某一步重跑」= fork 到那个 entry，不用自己设计版本模型 |
| **M6** Trajectory 视图 | 订阅上面整条事件流自建视图 | **pi 侧没有现成 UI**，这是唯一需要自己写的一块（dsh 有现成的，见 §4） |
| **D3** 自进化提案制 | `pi.registerCommand()` 把提案流程做成斜杠命令；`ctx.ui.*` 收人工裁决 | 判断留模型，确定性流程下沉成 command |

> 需求文档 §4 D1 推荐方案里那个 `HarnessAdapter` 的六个动作——起会话 / 发消息 / 注册工具 / 读会话流 / 派子 Agent / 取上下文用量——在 pi SDK 里有 1:1 的现成落点：
`createAgentSession()` / `session.prompt()` / `pi.registerTool()` / `session.subscribe()` + `ctx.sessionManager.getEntries()` / 官方 subagent example / `context` 事件。
也就是说 Adapter 不是「为了将来换地基」的额外抽象成本，它现在就有一个能跑的实现。
> 

### pi 刻意不内置、但有现成参照的三件事

pi 的设计取向是「小内核 + 扩展」，所以下面三样**不在内核里**，但都有官方 example 或社区实现：

- **sub-agents** → 官方 `examples/extensions/subagent`；社区 `nicobailon/pi-subagents`
- **plan mode** → 官方 `examples/extensions/plan-mode`
- **权限弹窗 / confirmation** → 官方 `permission-gate.ts`、`protected-paths.ts`、`sandbox`；社区 `pi-permissions`、`pi-permission-system`

对 Next-Step 来说这反而是好事：F1/F2 的行为细节你本来就要自己定义，内置一套反而要绕开。

## 3. dsh 到底强在哪、代价是什么

先说公道话：**dsh 的架构确实比 pi 更彻底**。它建在 Cordis 内核上（`vendor/cordis|loader|hmr|include|group|schemastery`），信条是「一切皆插件、没有特权内核」。

### dsh 真正值得眼馋的地方

| 能力 | dsh 的做法 | 对 Next-Step 的诱惑点 |
| --- | --- | --- |
| 工具级扩展点 | `tools/pre-execute`（放行 / 拒绝 / **询问**）、`ctx.tools.guard()`、`tools/execute`、`tools/post-execute`、`tools/result` | F1 的「询问」是一等状态，不是自己拼的 |
| 审批即服务 | `dsh-approval`、`dsh-ask-user` 独立包 | 审批不是散落在 hook 里的 if |
| UI 卡片 | `presentCall` / `presentResult` **必须是 args 的纯函数**，同一段代码同时跑直播流和会话回放；`output.presentationMeta` 随 `tool/result` 落盘 | 这条约束设计得很聪明：回放和直播天然一致 |
| Trajectory 视图 | `packages/client/ui-trajectory` 事件账本，0.1.0-rc.6 起默认进 web 组合 | **M6 想要的东西，dsh 已经做完了** |
| 生命周期与热更 | Fiber `PENDING→LOADING→ACTIVE→UNLOADING→DISPOSED`；`ctx.effect()` 逆序自动清理；HMR | 插件卸载不留垃圾 |
| 事件语义 | `emit` / `waterfall` / `parallel` / `serial` / `bail`，`waterfall` 的 `next()` 就是拦截网关 | 比单一 emit 表达力强 |
| GUI 可组装 | 约 30 个 `dsh-client-*` Web GUI 插件 | UI 也是插件，不是改组件树 |

### 代价（这些都是已核实的，不是猜测）

<aside>
🚧

**成熟度**：v0.1 developer preview（npm `0.1.0-rc.6`，2026-08-13 发布）。README 用全大写写着 **THERE WILL BE COMPATIBILITY-BREAKING CHANGES**。

</aside>

- **安全**：`dsh web` 暴露 60+ RPC 方法，只做 Host header 检查、**没有 auth**（Discussion #853，截至 2026-08-14 无维护者回应，仓库无 [SECURITY.md](http://SECURITY.md)）。
- **插件信任模型**：插件是无签名代码、无权限清单。`danger-full-access` 已有用户家目录被删的案例（issue #461）。
- **不接受外部 PR**：遇到内核 bug 只能等，或者维护自己的补丁——这和 F4「不 fork 上游」的精神冲突。
- **已知稳定性问题**：subagent spawn 循环、内存无界等 crash 类 issue 仍开放。
- **学习成本被低估**：要迁 dsh，实际要学的是 **Cordis 这套元框架**（Service Definition / Provider / Consumer 三分、`group` + `isolate` 服务隔离、`cordis.yml` 的 `insert` / 按 id 整块覆盖 / `!!js` 表达式 / profile bundle 分层）。这不是「换个 SDK」，是换一套世界观。
- **一个具体的坑**：持久化会话事件 `turn/*`、`step/*`、`tool/call` 并不是同名 Cordis 事件——必须监听 `session/event` 再判 `event.type`。文档里不显眼，写第一个插件时一定会踩。

> 换算成工期直觉：dsh 能省下 M6 的 UI 工作量，但要先付 Cordis 的学习税 + v0.1 的返工税 + 无 auth 的自建安全层。对一个 F3 明确写着「本地 / 纯文件 / 单用户」的项目，这笔交换不划算。
>

## 4. pi-web 的真实位置：好用的表现层，不合格的承重墙

`agegr/pi-web`（MIT，Next.js，`npx @agegr/pi-web@latest`，端口 30141，读 `~/.pi/agent`，含 `sessions/*.jsonl`，可用 `PI_CODING_AGENT_DIR` 换目录）现成给了不少东西：

- 会话工作区：context usage、cost、compaction 可视化
- **两种分支**：New session / Edit from here（正好对上 M4 的重跑直觉）
- 文件浏览 + Git diff、worktree 切换
- Web 配置面板（provider / 模型 / 插件包 / skills）、中英双语 UI

**但它有一个决定性短板**：

<aside>
🧨

pi-web **没有插件机制、没有 UI 槽位**。整个仓库对外暴露的扩展点只有一个浏览器事件 `pi-web:session-row-contextmenu`（原本是给 Electron 壳用的）。想加任何 UI，只能直接改 React 组件树。

</aside>

再叠加一个工程事实：4.4k stars、531 commits，但**几乎是单人项目**（agegr 一人 411 contributions）。把 Next-Step 的领域层（追溯链、提案制、块级 `sourceRef`、Trajectory）写进它的组件里，等于：

1. 每次上游更新都要手工合并 → 变相 fork → **违反 F4**；
2. 领域逻辑和 UI 耦合，未来换任何前端（含自建、含 dsh 的 client 插件）都要重写；
3. 逻辑正确性只能靠点 UI 验证，没法在 CLI 里跑测试。

**正确用法**：pi-web 当「先有个能看的界面」的加速器，以及 M1–M4 阶段的调试台。它读的是 `~/.pi/agent/sessions/*.jsonl`——只要领域数据是写进 session 条目（`appendEntry`）的，pi-web 就是**可替换的**，换掉它不损失任何数据。

## 6. 建议动作：D1 改判为「甲′」

### 落地顺序

1. **地基下移一层**：`HarnessAdapter` 的实现绑到 pi 的 SDK + 扩展 API（`createAgentSession` / `createAgentSessionRuntime` / `registerTool` / `registerCommand` / `appendEntry` / 事件订阅），**不绑 pi-web**。
2. **领域层写成 pi 扩展**：M1 的工具、F1 的闸门、M2 的 `sourceRef` 写入，全部在扩展里完成，可脱离任何 UI 单测。
3. **pi-web 只做视图**：不在其中放任何领域判断；它只渲染 session 条目。加自定义渲染优先走 `registerEntryRenderer()`（在 pi 侧），实在需要新页面时才动 React。
4. **M6 之前重新评估前端**：那时你手里已有完整事件流，届时再决定「继续 pi-web / 换 `@kkkiio/pi-web-ui` / 自建」，成本都很低——因为承重墙不在前端。

### 从 dsh 只抄两点（对应 N2「不迁 dsh」，抄设计不迁实现）

1. **append-only 会话日志、按来源可检视**：所有领域事件 append 进 session 条目，带来源标记，永不原地改写。这是 M2 + M4 的共同地基。
2. **审批是一等服务，不是散落的 if**：把 F1 的闸门抽成一个独立模块（一个「approval」扩展），对外只暴露 `请求批准 → 得到裁决` 接口。将来无论换 UI 还是换地基，这块都能整体搬走。

（可选第三点：借 dsh 的「presentation 必须是 args 的纯函数」这条约束——保证 Trajectory 回放和直播渲染一致。这是免费的设计纪律，现在就能立。）

### 需求文档需要同步修订的地方

| 位置 | 建议改动 |
| --- | --- |
| §4 D1 | 「甲：pi-web + 领域层」→「甲′：**pi SDK / 扩展 + 领域层**，pi-web 为可替换表现层」。乙（迁 dsh）标注「v0.1 破兼容 + web RPC 无 auth，暂不考虑」 |
| §4 D4 | 块级 `sourceRef` 的存储位置定为 `appendEntry` 自定义条目（明确「不进 LLM 上下文」这一属性） |
| §7 迁移清单 | 增加一条：确认现有 pi-web 改动里有多少是「领域逻辑」，需要迁回扩展层 |
| §8 风险 | 新增：pi-web 为单人维护项目，任何组件树改动都构成变相 fork 风险 |
| N2 | 保留「不迁 dsh」，但补一句「借用其两条设计（append-only 日志 / 审批即服务）」 |
| §4 新增 **D6** | 新增待拍板项：`DecisionPort`（交互端口）的两种实现与默认策略——CLI 直接 `ctx.ui`，Web / 无人值守走 `approval_request` 条目。详见 §7.3 |

## 7. 一核两壳：开发者好改基座 + 用户 UI/CLI 都能用

<aside>
🧭

**一句话架构**：领域逻辑全部住在一个**不认识 UI、也不认识 pi** 的纯 TS 内核里；中间用一层很薄的 pi 适配层把它接到 pi 的 Hook 上；CLI 和 Web 只是两个**壳**，共享同一份会话 JSONL。改基座功能 = 只改内核，两个壳不动。

</aside>

### 7.1 四层，只有一层认识 pi

| 层 | 里面放什么 | 依赖 | 谁改 / 改动频率 | 怎么测 |
| --- | --- | --- | --- | --- |
| **L0** 上游 pi | agent loop、会话树、内置工具 | — | **不改**，pin 版本（F4） | — |
| **L1** `next-step-core` 领域内核 | diff 解析、`sourceRef` 血缘图、提案状态机、重试策略、doc/code 模式规则、闸门判定 | **零 pi 依赖、零 UI 依赖**，纯 TS | 开发者主战场，约 90% 改动 | 纯单测，毫秒级，不需模型不需界面 |
| **L2** `next-step-pi` 适配层（= `HarnessAdapter`） | `registerTool` / `registerCommand` / `tool_call` 拦截 / `tool_result` 改写 / `appendEntry` / 事件订阅 | **只有这层 import pi** | 少量、稳定，只在新增能力时动 | `SessionManager.inMemory()`  • `createAgentSession()`，stub 掉模型跑集成测试 |
| **L3** 两个壳 | CLI 壳 = pi 本体；Web 壳 = pi-web 或自建薄壳 | 只读会话条目 | 几乎不改；**不得包含任何领域判断** | 手动 / E2E |

判断分层是不是坏了的单一标准：**删掉 Web 壳，CLI 应该什么都不少；删掉 CLI 壳，Web 应该什么都不少。**

### 7.2 两个壳共享的那份「唯一真相」

`~/.pi/agent/sessions/*.jsonl` 就是全部状态。不引入数据库（守住 F3「本地 / 纯文件 / 单用户」）。

- CLI 里跑的会话，Web 里能直接回放
- Web 里 fork 出的分支，CLI `/tree` 能看到
- `appendEntry()` 写的自定义条目也落在同一个文件，**且不进 LLM 上下文**——这就是双前端共享领域数据的官方通道
- 开发时用 `PI_CODING_AGENT_DIR` 指到一个沙盒目录，不污染自己真实的 `~/.pi`

### 7.3 最难的一环：同一个确认闸门，两个前端都能用

这是「UI + CLI 双前端」真正的技术难点。`ctx.ui.confirm()` 在终端里是阻塞式提示，Web 里没有这个东西。

<aside>
🚨

**千万不要在闸门里直接调 `ctx.ui`**，否则你会写两套 F1，且两套行为永远对不齐。

</aside>

把交互抽成一个端口，闸门只认端口：

```tsx
// L1 领域内核：只认这个接口，不知道有没有终端
 export interface DecisionPort {
   ask(req: ApprovalRequest): Promise<Decision>
 }
```

两个实现，都在 L2：

| 实现 | 适用场景 | 做法 |
| --- | --- | --- |
| `CliDecisionPort` | `pi` 终端交互 | 直接 `ctx.ui.select()` / `confirm()` / `input()` |
| `EntryDecisionPort` | Web 壳 / 无人值守 | ① `appendEntry({ type: "approval_request", status: "pending", … })`；② 等同一 session 里出现对应 `approval_response` 条目；③ 前端（或自动策略）写入该条目即解除阻塞 |

三个白拿的好处：

1. 每次批准 / 驳回都落在 append-only 日志里——**M2 追溯链和 M6 Trajectory 白拿这份数据**
2. 无人值守模式只是第三个 Port 实现（自动批准白名单），闸门逻辑一行不改
3. F1 的行为可以在 L1 单测里验（给个 fake Port），不需要真终端也不需要真浏览器

### 7.4 渲染不要写两遍：presentation 是数据，不是代码

注意一个容易踩的坑：`registerEntryRenderer()` **只影响 pi 的终端渲染**，pi-web 不认识你的自定义条目。所以规则定成：

> 自定义条目的 payload 里自带一段**纯数据**的 presentation（`title` / `badges` / `rows` / `diffRef`），两个前端各自只实现一个**通用渲染器**。
> 
- 终端：`registerEntryRenderer` 把这段数据画成文本
- Web：一个通用组件按同样的数据画成卡片
- 收益：**新增一种条目类型，两个前端都不用改**。这是 dsh「presentation 必须是 args 纯函数」那条纪律的降级版，成本几乎为零，且顺便保证回放与直播一致

### 7.5 Web 壳的两种接法（按阶段选，不用一步到位）

| 阶段 | 接法 | 交互能力 | 成本 |
| --- | --- | --- | --- |
| M1–M4 | pi-web 直接读 `~/.pi/agent/sessions/*.jsonl`（`PI_CODING_AGENT_DIR` 指目录） | 以只读 / 回放 / 调试为主；批准走 CLI 或自动策略 | 近乎零 |
| M5–M6 | 自建薄壳：用 SDK `createAgentSession()` 起会话，或用 `pi --mode rpc`（LF 分隔 JSONL）驱动一个 pi 进程 | 完整双向：能写 `approval_response`、能 `fork`、能订阅实时事件 | 中，但**只写壳、不写领域** |

两种接法下 L1 / L2 完全不变——这就是分层的收益兑现点。也意味着你**现在不必为前端选型纠结**，M6 前再拍。

### 7.6 开发者体验的具体配置

- **一个 monorepo**：`packages/core`（L1）、`packages/pi-ext`（L2）、`apps/web`（可选 L3）
- **扩展装载两档**：项目级 `.pi/extensions/` 用于开发（改完新起一个会话即生效），`~/.pi/agent/extensions/` 用于日常使用
- **pin 住 pi 版本**（`@earendil-works/pi-coding-agent`），升级走一次显式回归，不 fork
- **模式隔离靠能力而不靠 prompt**：doc 模式用 `tools` 白名单 / `excludeTools` 物理禁掉 `write`/`edit`（AC-1.3）
- **壳与扩展间不造 IPC**：直接用 `PI_SESSION_ID` / `PI_SESSION_FILE` / `PI_PROVIDER` / `PI_MODEL` 等环境变量
- **双前端回归用同一批用例**：一份 fixture session JSONL，分别在终端渲染器和 Web 通用组件上跑快照比对

### 7.7 一条必须提前定的规则：谁是 writer

CLI 和 Web 同时对一个 session 写会互相踩。定成：

<aside>
🔒

**一个 session 同一时刻只有一个 writer**。Web 想「写」就 `fork` 出自己的分支（`fork(entryId, { position: "at" })`），而不是往别人正在跑的会话里插条目。

</aside>

这条正好和 N8「并行 run 不承诺归因」一致。不要指望文件锁救你，也不要为了双写去引入数据库（那就破了 F3）。

### 7.8 落地顺序（每步都有可验收物）

1. 抽 `next-step-core`，把已有领域逻辑（含目前写在 pi-web 里的部分）搬进去，配单测 → 验收：不启动任何界面就能跑完全部逻辑测试
2. 写 `next-step-pi` 扩展：`registerTool` + `tool_call` 闸门 + `CliDecisionPort` → 验收：**纯 CLI 下 F1 已经能跑通**
3. 把闸门换成 `EntryDecisionPort`，批准请求 / 应答落盘为条目 → 验收：pi-web 里能**看到**待批准与历史裁决
4. 给 Web 壳加写入能力（SDK 或 `--mode rpc`）→ 验收：同一个闸门，终端和浏览器都能完成确认
5. 通用渲染器 + 事件流订阅 → M6 Trajectory
